Viewport Multi-Selection Compounding & Stale Packet Diagnosis

Executive Summary

When rotating between selected elements or changing tabs, elements previously selected persist their render commands into the viewport and compound, causing persistent flickering even without window resizing.

This document details the architectural root causes of this compounding behavior across devReplayPacket lifetime management, Vulkan GPU host-buffer memory hygiene, and multi-buffering frame-slot synchronization.

Technical Root Cause Analysis

1. DevUiReplayPacket Persistence Across Selection Changes & Tab Swaps

  • Location: FlowUi.cpp & DevInspectWorkbench.cpp
  • Mechanism: When an element is selected, requestDevUiReplay populates window.devReplayRequest, and captureDevUiReplayPacket extracts the matching render commands into window.devReplayPacket. However:
    • When switching tabs (e.g. from Preview tab to Overview tab), DevPreview::buildElement stops executing. requestDevUiReplay is never called.
    • window.devReplayPacket retains the commands and requestKey of the previously selected element in memory indefinitely.
    • When switching back to the Preview tab or selecting a layout node with 0 drawable commands, window.devReplayPacket continues serving stale commands from past selections.

2. GPU Host-Mapped Buffer Residual Memory Leaks (frameSlot.mappedData)

  • Location: DevPreviewViewPortRendering.cpp
  • Mechanism: In DevPreviewViewPortRenderer::record, cpuInstances are serialized and copied to Vulkan mapped host memory:
    const VkDeviceSize copySize = static_cast<VkDeviceSize>(
    impl_->cpuInstances.size() * sizeof(UiInstance));
    std::memcpy(frameSlot.mappedData, impl_->cpuInstances.data(), copySize);
    ensureCapacity allocates GPU buffers with a minimum capacity (e.g. 256 instances = 22,528 bytes). If Element A has 10 instances (880 bytes) and the user subsequently selects Element B with 3 instances (264 bytes):
    • memcpy overwrites the first 264 bytes.
    • Bytes 264 through 879 in frameSlot.mappedData continue to contain the raw UiInstance structs from Element A.
    • If a frame slot re-indexing mismatch or shader base index offset occurs, Vulkan draw calls sample uncleared instance data from previous selections, rendering ghost geometry from deselected elements into the viewport.

3. 1-Frame Asynchronous Key Mismatch (replay.requestKey vs. state.lastSelectedNodeKey)

  • Location: DevPreviewViewPortRendering.cpp
  • Mechanism: When the user selects a new element (key = B):
    1. In frame $N$, state.lastSelectedNodeKey updates to B, and requestDevUiReplay(B) is dispatched.
    2. The offscreen viewport render pass executes before App::prepareFrame captures the new replay packet.
    3. During frame $N$'s viewport pass, replay.requestKey is still A (stale packet from frame $N-1$), while state.lastSelectedNodeKey is B.
    4. The early return check if (replay.requestKey != state.lastSelectedNodeKey) return; triggers in DevPreviewViewPortRenderer::record.
    5. Result: The viewport target for frame $N$ receives zero draw commands (renders blank/clear). In frame $N+1$, captureDevUiReplayPacket completes, key B matches, and commands draw again. This 1-frame blank drop recurs on every selection rotation, manifesting as compounding flickering.

Recommended Remediation Architecture

  1. Synchronous Packet Invalidation on Selection Change: In App::requestDevUiReplay, if requestKey != window.devReplayPacket.requestKey, immediately clear window.devReplayPacket commands so stale replay packets never persist across selection switches or tab transitions.
  2. GPU Host Memory Hygiene: In DevPreviewViewPortRenderer::record, zero out remaining mapped buffer memory (frameSlot.mappedData) up to capacityBytes or track active buffer size so old UiInstance data cannot leak into subsequent draw calls.
  3. Graceful Pipeline Handling for Key Transitions: Handle 1-frame key transitions cleanly without dropping draw commands or leaving frame slots in uninitialized states.
