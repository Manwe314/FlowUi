Configuration glossary

This reference lists startup and operation configuration, their defaults, units, and build conditions. Core types live in FlowUi; development types retain their FlowUi::devSystems namespaces and headers under include/devSystems.

Include AppConfig.hpp to configure startup, and App.hpp for makeApplication(). Startup copies the configuration; editing the caller's original struct does not reconfigure the running application. Use explicit runtime APIs, such as App::setWindowInputConfig(), for supported live changes.

Capacity settings and precedence

MemoryCapacityProfile::storage supplies seven typed startup byte capacities for storage pools and buffers. settings supplies individual registered capacities by stable ID, including those same byte capacities and manager container reserves in bytes or entries. Each setting is an initial allocation hint; it does not impose a universal maximum on manager containers.

Startup resolves values in this order, with each later layer overriding matching targets:

  1. Owner defaults.
  2. Nonzero typed storage hints.
  3. Explicit settings entries.
  4. Available baked capacities when AppConfig::prefer_baked_capacities is true.

A zero typed storage hint preserves defaults. A zero explicit setting selects the target's registered default, overriding a matching typed hint. Unknown targets, conflicting caller duplicates, values above the registered maximum, and misaligned nonzero values reject application creation. Identical duplicates are accepted. growthFactor must be finite and greater than one; storage applies a minimum factor of 1.1. Growth also depends on allowRuntimeGrowth and the configured capacity error policies and budgets.

FlowUi::AppConfig config{};
config.prefer_baked_capacities = false; // Use caller hints for manual tuning.
config.memoryCapacityProfile.storage.initialInstanceBytesPerFrame =
4ull * 1024 * 1024; // 4 MiB per frame slot.
config.memoryCapacityProfile.settings.emplace_back(
FlowUi::MemoryCapacitySetting{
FlowUi::makeMemoryCapacityTargetId(
"flowui.tuning.input_fields.registry_entries"),
256 // Entries, as registered for this target.
});

Use the exact case-sensitive keys in the capacity catalog. The public ID helper hashes the key at compile time; application creation checks registration and value constraints. Capacity resolution runs at startup; owners retrieve resolved indexed values when reserving their containers or initializing pools.

MemoryCapacityProfile::metadata describes the evidence behind a profile and does not change allocations. Aggregate manager demand is retained separately in devSystems::MemoryCapacityPreview::managers for profiling; it is not part of startup configuration.

Development capture controls require FLOW_UI_DEV_MODE. Agentic controls additionally require AGENTIC_WORKFLOW, which generates FLOW_UI_AGENTIC_WORKFLOW. Icon settings require icon support. Settings for an omitted subsystem do not enable it.

Additional operation-level settings

These belong to their operation or element rather than AppConfig. Supply them to the relevant operation rather than adding them to startup configuration.

Managed windows and operation capabilities

ManagedWindowFlags has autoDestroyOnClose = true. A managed secondary window with this flag is destroyed after a close request during dispatch; disabling it leaves teardown to the caller. It is supplied to callback registration/window creation, not AppConfig.

WindowOperationCapabilities is returned by App::windowOperationCapabilities(). It reports backend support rather than requesting operations. Its close_window, minimize, maximize_restore and toggle_fullscreen fields all default to false; check the returned Result before reading them. App includes the checked call and operation examples.

Other authoring values and internal UI settings

Public style/resource descriptions are intentionally separate: FlowUiTheme, TextureRef, viewport API and descriptions, and FSEL. They configure particular elements/resources rather than library startup. Theme fields, texture descriptions, FSEL parameters, and Clay layouts are documented by their authoring APIs.

Developer-panel-only settings can remain internal. Examples are MemoryPlannerSettings, which holds reserve/percentile/margin/growth-factor choices for a what-if calculation, and MemoryHistoryLaneSettings, which holds panel source/scope/metric selections and resolved UI bookkeeping. They are not missing AppConfig members. Likewise DevFieldOptions and DevRolePolicy configure schema authoring, not startup.

Internal assembly types

StorageConfig and WindowStorageDesc assemble resolved capacities, budgets, frame arenas, and descriptor limits. AppWindowConfig combines native, Vulkan, and UI settings for a window. These remain implementation types; configure the supported startup and operation values described above.

Documentation and output locations

docs/ holds Markdown documentation and generated Doxygen output. Agentic screenshots, captures, logs, reports, and verification matrices, including Markdown reports, belong under .flowui/agentic/. Harness exports default to .flowui/agentic/verification/<suite>/; the standard evidence store is .flowui/agentic/v1/. See the agentic workflow guide.

Pass these exact keys to makeMemoryCapacityTargetId(). Defaults and alignment follow the capacity registry. The accepted maximum constrains the startup hint; it is not a command to allocate that maximum or a runtime growth ceiling. Zero selects the listed default, which can itself mean no explicit reserve.
