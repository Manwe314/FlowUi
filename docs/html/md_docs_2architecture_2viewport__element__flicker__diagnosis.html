Viewport Render Element Flickering & Extent Change Diagnosis

Executive Summary

When expanding the window or resizing the preview canvas, the rendered element in DevInspectWorkbench flickers between an in-world placed element and a screen-space glued version.

This document details the root causes behind this behavior, tracing the data pipeline from Clay render command replay capture (DevUiReplaySource) through offscreen Vulkan viewport rendering (DevPreviewViewPortRenderer) and UI sidecar overlay execution (DevPreviewCanvas).

Technical Root Cause Analysis

1. Scissor Box Intersection in Un-transformed Viewport Space

  • Location: Vk_UiRenderer.cpp & DevPreviewViewPortRendering.cpp
  • Mechanism: During viewport recording, DevPreviewViewPortRenderer::record passes ctx.extent (e.g. $800 \times 600$) into buildUiInstancesDirect. Inside BuildInstancesAndRunsFromClay, scissorStorage[0] (the root scissor) is initialized to {0.0f, 0.0f, extent.width, extent.height} in viewport canvas local space. When processing nested scissor commands (CLAY_RENDER_COMMAND_TYPE_SCISSOR_START), the command's bounding box is still in source window screen space (e.g. $x=450, y=200, w=300, h=150$). BuildInstancesAndRunsFromClay intersects clip (in source window space) with scissorStorage[0] (in viewport canvas space). When the viewport is small (e.g. $width=400$), $x=450$ is outside $[0, 400]$, causing Intersect to clip the scissor box to width $0$. When transformReplayGeometry runs afterwards on run.scissor, the scissor bounds were already clipped or corrupted prior to applying transformX (which subtracts $originX$). When the window expands, $x=450$ suddenly falls inside the un-transformed viewport extent, causing scissor regions to abruptly pop in and out between unclipped, clipped, and screen-space coordinates.

2. 1-Frame Asynchrony in Canvas Dimensions (previous.boundingBox vs. ctx.extent)

  • Location: DevInspectWorkbench.cpp
  • Mechanism: DevPreviewCanvas::buildElement queries Clay_GetElementData to retrieve previous.boundingBox from the previous frame's layout. During an active window expansion in frame $N$:
    1. state->canvasWidth retains the OLD canvas size (e.g. 400x300) during Clay UI construction.
    2. Visual sidecar overlays (drawPreviewSidecars), grid lines, and ruler guides use worldToCanvas with state->canvasWidth = 400, centering overlays at $(200, 150)$.
    3. Simultaneously, ViewPortManager::prepareFrameTargets updates the offscreen VkImage target to the NEW extent (e.g. 800x600).
    4. DevPreviewViewPortRenderer::record is executed with ctx.extent = 800x600, centering the offscreen rendered element at $(400, 300)$.
    5. Result: In frame $N$, the rendered Vulkan element inside the viewport image jumps to $(400, 300)$, while the Clay sidecar overlays remain at $(200, 150)$ (glued to screen space relative to old dimensions). In frame $N+1$, previous.boundingBox updates to 800x600, causing sidecars to jump to $(400, 300)$. This produce frame-to-frame visual tearing and flickering between screen space and world space positioning during continuous resize operations.

3. Replay Source Packet & Bounds Temporal Lag

  • Location: FlowUi.cpp & DevInspectWorkbench.cpp
  • Mechanism: DevPreview::buildElement issues a request via requestDevUiReplay(..., selection.clay->bounds) with the selected node bounds from the current frame. However, DevUiReplaySource (replay) passed into DevPreviewViewPortRenderer::record comes from window.devReplayPacket, which is captured during App::prepareFrame at the end of the pipeline. When expanding the main window, the inspected element's screen bounds ($originX, originY$) shift in the current frame, but replay.commands contain coordinates from the previous frame's layout. In transformReplayGeometry: $$\text{targetX} = (sourceX - originX - \text{panX}) \cdot \text{zoom} + \frac{canvasW}{2}$$ If $originX$ updates in frame $N$ while $sourceX$ originates from frame $N-1$, $sourceX - originX \neq 0$. The residual screen-space offset temporarily pushes the rendered element to raw screen coordinates rather than world origin $(0,0)$, creating the illusion of an element glued to screen space for 1 frame until packet synchronization catches up.

Recommended Remediation Steps (For Future Implementation)

  1. Transform Scissor Coordinates Before Clipping: In transformReplayGeometry, transform scissor bounding boxes into world coordinates before intersecting them with the viewport canvas extent, or isolate scissor bounding box logic from main window screen space.
  2. Synchronize Canvas Dimensions Before Overlay Emit: Update state->canvasWidth and state->canvasHeight dynamically using the current layout constraint or immediate container sizing rather than relying exclusively on previous.boundingBox from Clay_GetElementData.
  3. Synchronize Replay Packet Bounds with Replay Commands: Ensure sourceRootBounds inside DevUiReplayPacket strictly corresponds to the exact layout frame from which Clay_RenderCommandArray was captured.
